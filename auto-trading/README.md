# 업비트 그리드 트레이딩 봇

BTC/KRW 그리드 자동매매 프로그램입니다. `grid_engine.py` 하나로 동작합니다.

## ⚠️ 먼저 읽어주세요

**이 프로그램은 며칠 안에 원금을 2배로 만들어주는 도구가 아닙니다.**
그리드 트레이딩은 가격이 오르내리는 변동에서 수수료 이상의 작은 마진을
꾸준히 모으는 전략입니다. 짧은 기간에 큰 수익을 노리는 만큼 원금을
짧은 기간에 잃을 확률도 똑같이 커집니다.

이 코드가 실제로 하는 일:
- 왕복 수수료보다 마진이 작은 그리드는 애초에 만들지 않습니다 (구조적으로 적자 매매 차단).
- 평가자산이 `STOP_LOSS_PCT` 밑으로 떨어지면 **즉시 전량 취소하고 정지**합니다.
- 평가자산이 **시드 × `WITHDRAW_MULTIPLE`**(기본 5만원→10만원)에 도달하면
  시드금액만큼 출금하고, **정지하지 않고 남은 금액으로 계속 매매**합니다.
  이 사이클이 반복됩니다 (10만→시드 5만 출금, 남은 5만으로 계속→다시 10만→...).
- 처음 API 키로 실제 잔고를 확인해서, 설정한 자본보다 실제 잔고가 적으면
  실제 잔고 기준으로 방어적으로 운용합니다.

**실전 투입 전 권장 순서 (① → ⑥):**

| 단계 | 명령 | 확인하는 것 |
|---|---|---|
| ① 코드 실행 자체 확인 | `python grid_engine.py --check` | 설정값이 유효한지, 실제 주문은 전혀 안 나감 |
| ② 백테스트 | `python grid_engine.py --backtest` | 과거 데이터에서 전략이 말이 되는지 |
| ③ 모의(Mock) 몇 시간~하루 | `python grid_engine.py` (API 키 없이) | 그리드 생성/체결/재중심 로직이 실제로 도는지. `--dry-run`과 다르게 이 모드는 실제 "가상매매"를 합니다: 현재가가 매수가 아래로 내려오면 체결로 간주하고 BTC를 보유했다가 매도가에 팔아 손익을 계산합니다 |
| ④ 실제 API 연결, 주문은 차단 | `python grid_engine.py --dry-run` | 실제 시세·잔고·미체결주문 조회는 되지만 매수/매도/취소/출금은 **절대 전송 안 됨** (로그로만 확인) |
| ⑤ 소액 실거래 | `.env`에서 `TRADING_CAPITAL_KRW=50000`으로 `python grid_engine.py` | 진짜 5만원으로 실제 체결/재중심/손절이 도는지 |
| ⑥ 금액 확대 | `.env`에서 `TRADING_CAPITAL_KRW` 상향 | ⑤가 며칠간 문제없이 돌았을 때만 |

`--dry-run`은 API 키를 실제로 붙여서 진짜 시장 데이터·내 잔고·내 미체결
주문을 그대로 읽어오되, 주문을 내는 모든 메서드(매수/매도/취소/출금)를
거래소로 보내지 않고 로그에만 "[DRY-RUN] ... 생략"으로 남깁니다. ④단계에서
쓰세요.

봇을 재시작할 때마다(④~⑥ 전 과정에서 항상) 로컬 상태 파일이 아니라
**거래소의 실제 미체결 주문을 다시 조회해서 대조**합니다(아래 "재시작 시
안전장치" 참고). 이 대조만 따로 확인하고 싶으면:
```bash
python grid_engine.py --reconcile
```

## 설치

```bash
cd auto-trading
pip install -r requirements.txt
cp .env.example .env
# .env를 열어서 업비트 API 키와 설정값을 채우세요
```

**API 키 권한은 사용 방식에 따라 다르게 주세요:**
- `AUTO_WITHDRAW_ENABLED=false`(기본값, 권장) — "자산조회", "주문"만 체크하고
  **출금 권한은 주지 마세요.** 목표 도달 시 알림만 오고, 실제 출금은 업비트
  앱에서 직접 하는 방식입니다. 가장 안전합니다.
- `AUTO_WITHDRAW_ENABLED=true` — "출금하기" 권한까지 체크해야 합니다. 이 경우
  반드시 업비트 마이페이지에서 **출금 계좌를 사전에 등록**하고, API 키 발급 시
  **허용 IP**를 설정하세요 (둘 다 업비트 사이트에서 직접 해야 하는 수동 작업이며,
  이 프로그램이 대신해줄 수 없습니다). 신규/변경된 키는 업비트 정책상 최대
  72시간 출금이 제한될 수 있습니다.

## 실행

```bash
# 1) 설정값만 검증 (주문 없음, 가장 먼저 실행해보세요)
python grid_engine.py --check

# 2) 현재 시장 상태 확인
python grid_engine.py --status

# 3) 1회만 실행해서 로그 확인 (API 키 없으면 자동으로 모의 모드)
python grid_engine.py --once

# 4) 과거 데이터로 그리드 전략 성과 확인
python grid_engine.py --backtest

# 5) 실전/모의 무한 루프 (기본 3분 주기)
python grid_engine.py
python grid_engine.py --interval 180

# 6) (AUTO_WITHDRAW_ENABLED=false일 때) 업비트 앱에서 수동으로 시드를
#    "실제로 출금한 뒤" 이 명령으로 봇에게 알려서 기준선을 리셋
#    (yes를 입력해야 진행됨. 금액을 생략하면 현재 기준선만큼 출금한 것으로 간주)
python grid_engine.py --confirm-withdrawal
python grid_engine.py --confirm-withdrawal 45000   # 실제 출금액이 다르면 직접 지정

# 7) 실제 출금 API가 내 계정에서 동작하는지 소액으로 미리 테스트
python grid_engine.py --withdraw-now 10000
```

## GCP VM에서 24시간 돌리기

```bash
nohup python3 grid_engine.py > /dev/null 2>&1 &
# 또는 systemd 서비스로 등록해서 재부팅 시에도 자동 시작되게 하는 것을 권장합니다.
```

`Ctrl+C`(SIGINT) 또는 `kill`(SIGTERM)로 종료하면 미체결 주문은 그대로 두고
현재 상태만 `grid_state.json`에 저장한 뒤 종료합니다. 다시 실행하면 이어서
진행합니다.

## 파일

- `grid_engine.py` — 본체 (그리드 엔진 + 레짐 감지 + 리스크/출금 관리)
- `grid_state.json` — 그리드 현황, 누적 실현손익 (자동 생성)
- `risk_state.json` — 현재 기준선(시드), 누적 출금액 (자동 생성)
- `trading.log` — 실행 로그

## 재시작 시 안전장치 (실거래 전 반드시 확인해야 할 3가지)

실거래 투입 전 짚어야 할 세 가지 문제를 실제로 재현해서 고쳤습니다.

1. **재시작할 때 로컬 상태와 거래소 실제 주문을 대조하지 않던 문제.**
   프로그램을 껐다 켜면(`grid_state.json`이 유실됐거나, 그 사이 업비트 앱에서
   직접 주문을 냈거나) 거래소에는 주문이 있는데 프로그램은 모르는 상황이
   생길 수 있었습니다. → `GridBot`을 시작할 때마다(`--reconcile`로 단독
   실행도 가능) `reconcile_with_exchange()`가 자동으로:
   - 로컬에 있는 주문들을 실제 상태로 재조회해서, 꺼져 있던 동안 체결/취소/
     부분체결된 것을 반영하고,
   - 거래소에는 있지만 로컬 상태 파일엔 없는 미체결 주문을 찾아서 자동으로
     편입합니다 (단, 매수단가를 알 수 없는 매도주문이 편입된 경우 그 건의
     손익 계산은 생략하고 명확히 로그로 표시합니다 — 모르는 값을 추정해서
     섞지 않습니다).

2. **부분 체결 처리 부족.** 매수/매도 주문이 일부만 체결된 상태에서 그 주문을
   취소하면(재중심, 손절 등) 이미 체결된 부분을 그냥 버리던 문제. →
   `cancel_order()`가 이제 취소 직전 체결량을 반환하고, 그 수량이 있으면
   `sell_retry` 상태로 돌려 다음 사이클에 반드시 매도를 재시도합니다. 거래소
   에서 외부적으로(업비트 앱 등) 주문이 취소/부분체결된 경우도 동일하게
   회수합니다.

3. **손절 시 `cancel_all()`이 매도 대기(pending_sell) 주문의 BTC를 정리하지
   못하던 문제.** 기존 `cancel_all()`은 아직 체결 안 된 매수 주문만 취소하고,
   이미 걸어둔 매도 주문은 의도적으로 남겨뒀습니다(평소엔 맞는 동작 — 익절
   기회를 살려두려고). 근데 손절처럼 "전량 즉시 청산"이 필요한 순간에 이
   로직을 그대로 쓰면 매도 대기 중인 BTC가 여전히 시장에 묶인 채 남습니다.
   → 손절 전용 `liquidate_all()`을 새로 만들어 매수 대기 + 매도 대기 주문을
   전부 취소해서 BTC를 자유잔고로 회수한 뒤, 그 다음에 시장가로 전량
   매도합니다. 평소 재중심 때 쓰는 `cancel_all()`은 그대로 두고, 손절
   (`RiskManager.check_stop_loss`)만 `liquidate_all()`을 쓰도록 분리했습니다.

세 가지 모두 페이크 거래소(주문 상태를 자유롭게 조작 가능한 테스트용 모의
객체)를 붙여서 재시작/부분체결/외부취소 시나리오를 실제로 재현해 검증했습니다.

## 5만원 실투입 직전에 추가로 잡은 것 (실계좌 검토 피드백 반영)

1. **평가자산(equity) 계산이 `free` 잔고만 봤던 문제.** 매수 주문을 걸면 그만큼
   KRW가 `used`(묶임)로 빠지고, 매도 주문을 걸면 그만큼 BTC가 `used`로 빠집니다.
   기존 `get_equity()`는 `free`만 더해서, **미체결 주문이 떠 있는 동안 실제로는
   잃지 않은 자산을 "없어진 것"처럼 계산**할 수 있었습니다 — 이 값이 손절선/
   출금 판단에 직결되므로 허위 손절이 발동할 수 있는 심각한 문제였습니다.
   → `get_balance()`가 `free`뿐 아니라 `free+used`(=`total`) 값도 함께
   반환하도록 고치고, `get_equity()`는 실거래 모드에서 반드시 `total` 기준으로
   계산하도록 수정했습니다. (자유 잔고가 필요한 다른 계산 — 출금 재원 확인,
   시장가 청산 수량 — 은 원래대로 `free`를 씁니다.)
2. **`--confirm-withdrawal`이 실제 출금 여부·금액을 확인하지 않던 문제.**
   기존엔 무조건 `CAPITAL`(설정된 시드값)만큼 출금했다고 간주했고, 여러 번
   출금 사이클을 거쳐 기준선(`baseline`)이 `CAPITAL`과 달라진 뒤에도 그 사실을
   반영하지 못했습니다. 실수로 명령만 실행해도 기준선이 조용히 바뀔 수
   있었습니다. → 금액을 생략하면 `CAPITAL`이 아니라 **그 시점의 실제
   기준선**(`risk_state.json`)을 기본값으로 쓰고, 다른 금액을 출금했다면
   `--confirm-withdrawal 45000`처럼 직접 지정할 수 있게 했습니다. 또한 실행
   시 "정말 출금하셨습니까? yes 입력" 확인을 반드시 거치도록 해서, 실수로
   실행해도 명시적으로 확인하지 않으면 아무것도 바뀌지 않습니다.
3. **`DRY_RUN`과 모의(Mock) 모드는 다른 것입니다.** `--dry-run`은 실제 API
   키로 시세·잔고·미체결주문을 그대로 읽되 주문 전송만 막는 "연결 점검"
   용도이고, API 키 없이 실행하는 **모의 모드가 실제 가상매매(paper
   trading)** 역할을 합니다 — 위 ①~⑥ 표에서 ③번이 그 역할이고, 진짜
   50,000원이 매수·매도되며 잔고가 바뀌는 과정을 시뮬레이션합니다.
4. TREND_DOWN(하락 추세) 진입 시 자본이 절반으로 줄어드는 것까지 고려해도
   레벨당 금액이 최소주문금액을 넘는지, `validate_config()`가 시작 시점에
   같이 검증하도록 보강했습니다 (기존엔 평상시 자본 기준만 검증해서, 설정에
   따라 하락장에 진입해서야 막히는 경우가 있었습니다).

이 네 가지도 실제 코드를 실행해서 (free/used를 섞은 가짜 잔고 응답, 여러
출금 사이클을 거친 뒤의 기준선 등) 검증했습니다.

## 시드 출금 사이클이 동작하는 방식

1. 시드 5만원으로 그리드 매매 시작 (`baseline` = 50,000)
2. 평가자산이 `baseline × WITHDRAW_MULTIPLE`(기본 10만원)에 도달
3. `AUTO_WITHDRAW_ENABLED=false`(기본) → 로그에 알림, 사람이 업비트 앱에서
   5만원 수동 출금 → `--confirm-withdrawal` 실행
   `AUTO_WITHDRAW_ENABLED=true` → 봇이 자동으로 5만원 출금 API 호출
4. 출금이 확정되면 `baseline`이 "그 시점의 남은 평가자산"으로 갱신됨
   (보통 다시 ~5만원 근처) → 다음 목표는 새 baseline × 2
5. 봇은 멈추지 않고 계속 이 사이클을 반복합니다.

손절선(`STOP_LOSS_PCT`)도 이 `baseline` 기준으로 다시 계산되므로, 출금 이후
"지금 굴리고 있는 시드"를 기준으로 보호가 계속 유지됩니다.

## 설정값 (.env)

| 변수 | 기본값 | 설명 |
|---|---|---|
| `UPBIT_ACCESS_KEY` / `UPBIT_SECRET_KEY` | (없음) | 비우면 모의 모드 |
| `TRADING_CAPITAL_KRW` | 50000 | 시드(원금) |
| `STOP_LOSS_PCT` | 0.85 | 기준선의 이 비율 밑이면 전량 정지 (0.85=15% 손실 허용) |
| `WITHDRAW_MULTIPLE` | 2.0 | 기준선의 이 배수 도달 시 출금 트리거 |
| `AUTO_WITHDRAW_ENABLED` | false | true면 실제 출금 API 자동 호출 |
| `WITHDRAW_ALERT_COOLDOWN_SEC` | 3600 | 출금 알림 반복 간격(초) |
| `GRID_LEVELS` | 4 | 그리드 단계 수 |
| `GRID_MIN_PCT` | 0.006 | 최소 그리드 간격(현재가 대비 %, 수수료 손실 방지) |
| `DRY_RUN` | false | true면(또는 `--dry-run`) 조회는 실제로, 주문/취소/출금은 전부 생략 |

## 이전 버전 대비 수정된 부분

실제 실행 테스트로 확인된 이전 버전의 문제와 수정 내역입니다.

1. **그리드 절반 체결 후 영구 고정 버그** — 일부 레벨만 체결되면 그 뒤로는
   가격이 계속 움직여도 그리드가 다시 짜이지 않던 문제. → 가격이 그리드
   중심에서 `RECENTER_MULT × 간격` 이상 벗어나면 자동 재중심하도록 수정.
2. **매도 완료된 레벨이 영구 점유** — 매도까지 끝난 가격대를 다시 못 쓰던
   문제. → 매도 체결 확인 시 해당 레벨을 완전히 회수(삭제)해서 재사용 가능.
